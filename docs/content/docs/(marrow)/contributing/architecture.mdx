Marrow is a compiler with a browser runtime attached. Text goes in, a validated
model comes out, geometry is computed and checked, and two renderers turn it
into either SVG or canvas inside a self-contained page.

## Stage by stage

### schema — text to model

One validation code path. YAML is parsed with positions preserved so every
diagnostic can point at an exact line and column. Validation is strict: unknown
keys are errors, `x-` prefixed keys are preserved and ignored. Output is the
normalized `Topology` — the single in-memory shape every downstream module
consumes.

### layout — model to geometry

**Classify** picks one of six archetypes; declared structure (zones, tiers)
always outranks inferred shape. **Size** measures each node at the exact pixel
size and letter-spacing the renderers use, via static glyph tables in
`@marrow/metrics` — measurement must be deterministic and identical across
machines, which rules out asking a browser.

**Place** runs the engine that suits the archetype: ELK layered for zoned,
tiered, and flat; a compose pass to pack zone mosaics; polar for hub-spoke;
circular for rings and meshes. Radial presets allocate arc space from actual
node widths, so they're overlap-free by construction.

**Route** uses libavoid for orthogonal routing, polylines for radial shapes
(orthogonal channels look wrong on a ring).

**Tidy** applies cable-tray discipline: merge same-pair parallels onto one
visible stroke, pull fan-outs onto shared gutter lanes, order draws so alarms
sit above healthy runs. On a real HQ zone this took 165 links down to 36 unique
geometries.

### scene — the contract

Boxes and polylines, plus geometry helpers. Everything downstream speaks this
and nothing else. Port chips are scene geometry, placed collision-free by the
layout stage; renderers draw them verbatim rather than inventing positions.

### lint — the gate

The geometry linter runs before anything renders. L1 defects fail the build:
node overlap on label-inclusive boxes, edge segments through foreign node
interiors, endpoints not touching their node's box, port-chip overlap. L2
auto-repairs; L3 advises.

### visual — how geometry is painted

`@marrow/visual` owns the visual language: link semantics → symbol, px widths
and dashes, status colours and draw order, chip/LED proportions, and the theme
tokens behind them. Its per-dimension tables compile into one ordered paint
rule list (base → speed → mode → flow → status → path/selection). The list has
two interpreters: `resolveScene` / `interactEdge` fold it for imperative
drawing, and `visualCss()` prints it as class-driven CSS that only references
theme variables. Because both read the same list, the tiers cannot disagree —
a parity test evaluates the generated cascade against the fold for every
combination.

### render-svg and canvas-engine — paint to pixels

Two renderers, one visual language. SVG is the hero tier — full fidelity,
crisp at any zoom, SVG export. The canvas host is the scale tier, used when the
node count would make SVG unusable. **Both consume `@marrow/visual`**:
render-svg translates the resolved paint into classed markup; the canvas engine
turns the same paint into draw calls (a cached `Path2D` per edge from the shared
path `d`, so both tiers draw the exact same curve). A visual change lands in
`visual`; the renderers only change for markup or draw-call plumbing.

Shared conventions worth knowing before touching either:

- **Corner-anchored indicators.** Status LED and badge sit centered on the chip's corner arc at 45°, offset `r·(1−1/√2)` (computed once in `visual`). Both get a 2 px background halo ring.
- **Dashes are px.** Edges carry their own `--len` for the draw-in; nothing uses `pathLength`, so status and mode dashes render at a fixed rhythm on any edge length.
- **Background-halo knockout.** Anything an edge may cross — node labels, zone titles — uses `paint-order: stroke; stroke: var(--bg)` in SVG and `strokeText` on canvas, and sits in a layer above the edges. A crossing link is knocked out cleanly instead of slicing through letters.
- **Measure what you draw.** SVG pins labels with `textLength`; canvas condenses (never stretches) using a cached `measureText`.

### site — pages and packaging

One compile entry, `createSiteBuilder(topology, options)`, serves both output
shapes. It fills in build-wide defaults (the config file's `layout:` density
and scale, on a copy — never the caller's topology), then asks the planner for
the shape and the page set. The planner is the only place that decides a
**Single file** versus a **Site**; `options.shape` overrides it, which is all
`--single` does. A Single file is simply a plan with one page, `index.html`,
whose styles and runtime are inlined; a Site's pages share external assets.

Collapse decides what's summarized on each page. The compiler inlines the icon
sprites actually used. Page builds are content-hashed and memoized, so a
rebuild only touches pages whose inputs changed. Callers — the CLI and the dev
server — never plan, default or branch on the shape themselves: they pass
options and read pages back.

The chrome (`site/src/chrome.ts`, markup by feature under `chrome/`) is written
against the **page contract** — `runtime/src/shared/page-contract.ts`, imported
by both the compiler and the runtime. Every element the runtime binds to
carries a `data-m="<hook>"` behaviour hook from its `HOOKS` registry; classes
are for styling only. The embedded payload is `EmbeddedData`, picked from the
model through explicit key lists (a new model field reaches the browser only
when it is added to them) and serialized with `encodePageData`. The pre-boot
`<head>` script is a bundle of the same URL-parsing code the runtime uses, so
embed and kiosk options apply before first paint.

### runtime — the client

Camera, inspector, spotlight, minimap, search, export, command palette. The
chrome is shadcn/ui ported to vanilla CSS and TypeScript — never installed as
components, because output must stay dependency-free.

The runtime reads the page only through the page contract: `find` / `findAll`
look elements up by hook and throw a `HookError` naming it when the markup and
the runtime disagree, `boot()` branches on the payload's `kind` (diagram stage
or inventory), and `applyModularParams` is the one writer of the `<html>` state
attributes. Diagram elements are found through the stage hooks `@marrow/visual`
exports beside the classes it paints. Two bundles come out of the package:
`dist/runtime.js` and the ~1.5 KB `dist/preboot.js` inlined into every page's
`<head>`. The boot tests build real pages and run the runtime against them in
happy-dom, so a renamed hook fails the suite, not the viewer.

### server and cli

The dev server watches, rebuilds, and pushes live reloads over SSE, with a
small JSON API. It holds one builder for either output shape and serves every
page through the same path, so a served page is byte-identical to the built
one plus the live-reload client. The CLI is the user-facing surface: validate, build, serve,
snapshot, import, icons, schema.

## Design invariants

These are the properties the whole design serves. Breaking one is a bug, not a
trade-off:

1. **Determinism.** Same input, byte-identical output.
2. **Self-containment.** No network requests when a diagram opens.
3. **Declared meaning.** Nothing is inferred from names.
4. **Machine-readable diagnostics.** Every error has a stable code and a fix hint.
5. **Overlap-free geometry.** Enforced by the linter, not by hope.
