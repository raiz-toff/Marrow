A built diagram is an HTML document, not a fragment. That makes embedding
simple and slightly opinionated: you embed it in an `<iframe>` rather than
splicing its markup into your page.

## The basic embed

```html
<iframe
  src="/diagrams/branch.html"
  title="Branch office network"
  loading="lazy"
  style="width:100%; height:640px; border:1px solid #27272a; border-radius:12px"
></iframe>
```

That's the whole integration. The diagram brings its own styles and runtime, so
it cannot collide with your site's CSS — which is exactly why the iframe is the
right container rather than a limitation.

Height matters more than width. A network diagram in a 300 px strip is
unreadable; 560–720 px is a sensible range for an inline figure, and a
full-viewport height for a dedicated page.

## Embed and kiosk modes

When embedding a diagram inside a dashboard, blog post, or kiosk display, strip the surrounding chrome with URL parameters, in the query string or the hash:

```html
<!-- Minimal chrome: command bar, breadcrumbs, sidebar, backdrop, watermark,
     minimap and mobile bar hidden; the canvas and its controls stay live -->
<iframe
  src="/diagrams/branch.html?chrome=minimal"
  title="Branch office network"
  style="width:100%; height:600px; border:none;"
></iframe>
```

A small script at the top of `<head>` reads the parameters and sets attributes
on `<html>` before first paint, so the full chrome never flashes:

| Parameter | Values | Effect |
| :--- | :--- | :--- |
| `chrome` | `minimal` \| `full` | `minimal` hides the command bar, breadcrumbs, sidebar, backdrop, watermark, minimap and, on phones, the mobile bar. Zoom controls, pan, selection, tooltips and the inspector stay. |
| `embed` | `true` \| `false` | Shorthand for `chrome=minimal` / `chrome=full`. |
| `inspector` | `off` \| `on` | `off` keeps the inspector drawer closed when a device or link is clicked. |
| `minimap` | `off` \| `on` | `off` hides the minimap. |
| `controls` | `off` \| `on` | `off` hides the zoom controls. |
| `theme` | `dark` \| `light` | Overrides the authored theme for this view. |
| `d` | device id | Selects that device and flies the camera to it (hash only: `#d=core-sw-01`). |
| `c` | `x,y,k` | Camera centre and zoom (hash only: `#c=120,-40,1.5`). |
| `export_title` | `on` \| `off` | Title block on PNG/SVG exports. |
| `export_legend` | `on` \| `off` | Auto-legend on exports. |
| `export_ports` | `on` \| `off` | Port chips forced visible on exports. |


Combine them in the query (`?chrome=minimal&inspector=off`) or the hash
(`#chrome=minimal;inspector=off;minimap=off` — pairs are `;`-separated, `&`
also works). When both name the same parameter, the query wins.

**Flags are sticky.** A parameter that is absent changes nothing: dropping
`minimap=off` from the hash leaves the minimap hidden. To undo a flag, set its
opposite explicitly — `chrome=full`, `minimap=on`, `inspector=on`. Because a hash
change does not reload the page, a host can switch modes live by setting
`iframe.src = url + '#chrome=full'`.

**The diagram writes its own hash.** Selecting a device rewrites it (`d=…`);
the kiosk flags (`chrome`, `inspector`, `minimap`, `controls`) survive that
rewrite, and links between the pages of a multi-page site carry them along.

## Theme

A diagram carries the theme from its topology's `theme:` key — `dark`, `light`,
or `auto`. In an embed you usually want it to match the host page, and there are
two ways to get that without rebuilding the file.

### Follow the viewer's OS — `theme: auto`

```yaml
theme: auto
```

The diagram resolves `dark`/`light` from the viewer's `prefers-color-scheme`
before it paints, and switches live if they change it. No host code — a sensible
default for a diagram embedded on a site that itself follows the OS.

### Follow the host's own toggle — `postMessage`

If your page has its own light/dark switch, drive the diagram over `postMessage`.
The diagram announces itself when its runtime is ready; answer with the theme,
and re-send whenever yours changes:

```js
const frame = document.querySelector('iframe.marrow');

addEventListener('message', (e) => {
  if (e.data?.type === 'marrow:ready') sendTheme();   // answer the ready ping
});
function sendTheme() {
  const theme = document.documentElement.classList.contains('dark') ? 'dark' : 'light';
  frame.contentWindow.postMessage({ type: 'marrow:theme', theme }, '*');
}
```

The message is `{ type: 'marrow:theme', theme: 'dark' | 'light' | 'auto' }`. A
host-driven theme overrides the baked `theme:` and isn't persisted — opening the
same file standalone still shows its authored theme — and it works whatever
`theme:` the file was built with.

`marrow:ready` arrives after the diagram has painted, so a theme sent only in
reply to it shows the baked theme for a moment first. To avoid that flash, put
the host's current theme on the URL as well (`#theme=dark`) and use the message
for later changes — which is what `<MarrowEmbed />` does. Check `e.source`
against your iframe's `contentWindow` when a page holds several diagrams.

## React & Next.js component (`<MarrowEmbed />`)

For React apps (Next.js, Vite, …) there is a `<MarrowEmbed />` component. It is
distributed through Marrow's shadcn registry — the source is copied into your
codebase, nothing is installed from npm under a Marrow name:

```bash
npx shadcn@latest add https://marrowdiagram.vercel.app/r/topology-canvas.json
```

That writes `components/marrow/topology-canvas.tsx` and
`components/marrow/topology-types.ts`, and installs `lucide-react`, `clsx` and
`tailwind-merge`. The components use the standard shadcn theme tokens
(`bg-card`, `border-border`, `text-muted-foreground`, …). Inside a Marrow checkout,
`npm run marrow -- add topology-canvas --out <dir>` copies the same files.

```tsx
import { MarrowEmbed } from '@/components/marrow/topology-canvas';

export function NetworkDashboard() {
  return (
    <MarrowEmbed
      src="/diagrams/campus.html"
      title="Campus core network"
      chrome="minimal"
      theme="auto"
      aspectRatio="16 / 9"
      onError={(err) => console.warn(err.message)}
    />
  );
}
```

What it does for you:

- **Flags before first paint.** `chrome`, `inspector`, `minimap` and the theme go
  on the frame's URL hash, so the diagram's pre-boot script applies them.
- **Theme without a flash.** With `theme="auto"` it resolves the host's theme when
  the frame first loads — a `dark`/`light` class or `data-theme` on `<html>`,
  else `prefers-color-scheme` — and puts it on the URL; later host changes are
  sent over `postMessage`. The frame starts loading after hydration, so the
  ready handshake is never missed.
- **Load errors.** Success is the diagram's `marrow:ready` message. If none
  arrives within `loadTimeout` (8 s) it calls `onError` and shows `fallback`.
- **Several embeds per page.** Messages are matched to their own frame
  (`e.source`).
- **Fullscreen** through the Fullscreen API, or a fixed full-viewport overlay
  where that API is missing (iOS Safari); Escape leaves it.

See the [component reference](/docs/components/topology-canvas) for every prop.

### Compiled markup instead of a URL (`html`)

`html` renders a compiled diagram from a string through `srcdoc`. A srcdoc
document has no URL to carry parameters, so the component writes the same flags
straight onto its `<html>` element (`data-chrome`, `data-inspector`,
`data-minimap`, `data-theme`) before handing it to the frame. Two consequences:

- **It inherits your page's Content Security Policy.** The diagram's inline
  script and styles then need `'unsafe-inline'` (or their hashes) in *your*
  `script-src` and `style-src`, and PNG export needs `blob:` in `img-src`. A
  `src` URL is a separate document with its own policy.
- **It is same-origin with your page,** so `window.marrow` (below) is reachable
  through the component's `ref`:

```tsx
const frame = useRef<HTMLIFrameElement>(null);
// …
<MarrowEmbed ref={frame} html={compiled} onReady={() => frame.current?.contentWindow?.marrow?.selectDevice('core-sw-01')} />
```

## Linking straight to a device

Multi-page sites have real URLs, so you can deep-link:

```
/diagrams/global/index.html              overview
/diagrams/global/zones/campus.html       one zone
/diagrams/global/devices/core-sw-01.html one device
/diagrams/global/inventory.html          the table
```

Linking to a device page from a runbook is often more useful than embedding the
whole diagram.

## Content Security Policy

The output loads nothing external, so a strict policy is fine. What it *does*
need is inline styles and inline script — everything is inlined by design — and
`blob:` images, which is how PNG export rasterizes the diagram:

```
frame-src 'self';
```

on the host page, and for the diagram document itself:

```
default-src 'none'; img-src 'self' data: blob:; style-src 'unsafe-inline'; script-src 'unsafe-inline';
```

A diagram rendered through `srcdoc` (the component's `html` prop) has no policy
of its own: it runs under the host page's, so those sources must be allowed
there.

<Callout type="warn">
If your platform forbids inline script outright, single-file output won't run
there. Use the multi-page site shape instead — its runtime and styles are
separate files under `assets/`, which a hash- or nonce-based policy can
handle.
</Callout>

## JavaScript Client API (`window.marrow`)

Every diagram exposes a global `window.marrow` object for camera navigation, selection, events and custom inspector tabs. It lives in the diagram's own window: a host reaches it as `iframe.contentWindow.marrow`, which browsers allow only when the diagram is **same-origin** with the host (served from the same origin, or rendered through `srcdoc`). Cross-origin, use the URL parameters and `postMessage` above.

### Programmatic camera and selection

Host portals can control focus and camera movement directly (`marrow` below is
`iframe.contentWindow.marrow`, or `window.marrow` from a script inside the diagram):

```javascript
// Focus a specific device and smoothly fly camera to it
marrow.selectDevice('core-sw-01', true);

// Select an interconnect cable and open the link inspector
marrow.selectLink('core-sw-01--dist-sw-01#0');

// Clear selection and close inspector drawer
marrow.deselect();

// Retrieve currently inspected item
const current = marrow.getSelected();
// returns { type: 'device', item: DataDevice } | { type: 'edge', item: DataLink } | null

// Open the "About this diagram" document modal
marrow.openAbout();
```

### Event listeners

Subscribe to viewer interactions using `marrow.on(event, handler)`:

```javascript
// Listen for selection changes (device or link)
const unsubSelect = marrow.on('select', (selection) => {
  console.log('Selected:', selection.type, selection.item.name ?? selection.item.id);
});

// Listen for deselection
const unsubDeselect = marrow.on('deselect', () => {
  console.log('Selection cleared');
});

// Listen for inspector tab switches
const unsubTab = marrow.on('tabchange', (tabId) => {
  console.log('Active inspector tab:', tabId);
});
```

### Dynamic custom inspector tabs

Host applications can inject custom tabs into the inspector drawer dynamically at runtime:

```javascript
// Register a live telemetry tab with custom DOM rendering and cleanup
const unregister = marrow.inspector.registerTab({
  id: 'live-telemetry',
  label: 'Live Telemetry',
  target: 'device', // 'device' | 'edge' | 'both'
  order: 40,
  visible: (device) => device.role === 'router',
  render: (device, container) => {
    container.innerHTML = `
      <div class="m-inspector-section">
        <h3>Live Traffic (${device.name})</h3>
        <p>Inbound: 14.2 Gbps · Outbound: 9.8 Gbps</p>
      </div>
    `;
    const interval = setInterval(() => {
      // Poll or update live stats
    }, 2000);

    // Return cleanup callback invoked when tab is closed or selection changes
    return () => clearInterval(interval);
  },
});
```

## Keeping it current in CI

The diagram is generated, so treat it like any other build artifact. A minimal
GitHub Actions job:

```yaml title=".github/workflows/diagrams.yml"
name: diagrams
on:
  push:
    paths: ['input/**.yaml']

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 24 }
      - run: npm ci && npm run compile
      - run: npm run marrow -- icons fetch --yes      # if you use cloud packs
      - run: npm run marrow -- validate input/*.yaml  # exit 1 on errors
      - run: npm run marrow -- build input/branch.yaml -o site/diagrams/branch.html
      - uses: actions/upload-artifact@v4
        with: { name: diagrams, path: site/diagrams }
```

`validate` exits **1** on validation errors and **2** on usage or I/O errors, so
it gates a pipeline correctly with no extra scripting. Add `--json` if you want
to post the diagnostics somewhere.

Because output is deterministic, committing the built HTML produces a clean
diff: the file only changes when the topology actually changed.
